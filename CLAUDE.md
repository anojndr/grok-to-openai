# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm start          # start the bridge (loads .env, listens on HOST:PORT)
npm run dev        # same, with node --watch
npm test           # full suite via node --test (test/*.test.js)
node --test test/<file>.test.js                            # single file
node --test --test-name-pattern="<regex>" test/<file>.test.js   # single test
```

ESM (`"type": "module"`), Node >= 20, no linter/typecheck. Tests are `node:test` + `node:assert/strict`. Tests stub out the Playwright layer (`BrowserSession` methods are monkey-patched; the Grok API is simulated by driving the request/binding callbacks), so the suite runs without a real browser or network. `test/server.test.js` is the exception: it spawns a real `src/server.js` child process against a temp `DATA_DIR`.

## Development workflow

These rules apply to every change, no exceptions:

1. **Red/green TDD.** Write the failing test first, watch it fail (red), then implement the minimal change that makes it pass (green). Iterate with a single file: `node --test test/<file>.test.js`, or `node --test --test-name-pattern="<regex>" test/<file>.test.js` for one test. Match the style of the existing suites (`node:test` + `node:assert/strict`).
2. **Quality gates at the end.** Before a task counts as done, run the full suite (`npm test`) and confirm every test passes, then review `git diff` / `git status` to make sure no stray or unrelated files are left behind.
3. **Keep `.gitignore` and `README.md` up to date.** Any change that adds a new env var, endpoint, feature, or behavioral difference must be reflected in the README (endpoints, env list, compatibility notes); any new generated/runtime artifact, directory, or secret file must be added to `.gitignore`. Do this in the same change, not as a follow-up.

## What this is

An OpenAI-compatible bridge over authenticated `grok.com` web sessions. It does **not** use the xAI API: `src/server.js` (Express) translates OpenAI requests (`/v1/responses`, `/v1/chat/completions`, `/v1/files`) into calls to Grok's internal `/rest/app-chat/*` endpoints, executed inside a Playwright-controlled Chrome page so the site's anti-bot checks pass.

## Architecture

Two sides, connected by a state object:

- `src/openai/` — request/response translation. `schema.js` (zod) validates OpenAI payloads; `input.js` normalizes inputs (string / message array / `input_file` / `input_image` / remote URLs / Base64 / `file_id`) into `{ messages, instructions }` where `system`/`developer` roles become Grok custom instructions; `response-object.js` / `chat-completions.js` build the OpenAI envelopes; `sse.js` writes Responses SSE events.
- `src/grok/` — drives Grok. `client.js` (`GrokClient`) is the conversation API; `account-pool.js` (`GrokAccountPool`) is the multi-account runtime; `browser-session.js` (`BrowserSession`) is the Playwright bridge; `stream-parser.js`, `output.js`, `source-attribution.js`, `generated-images.js`, `thought.js` consume/transform the Grok stream.

### The browser bridge (browser-session.js)

This is the heart and the most fragile part. Grok's anti-bot layer requires request headers only the page can produce, so all `/rest/*` traffic runs through `window.fetch` inside the page:

1. `installGrokBridgePageHelpers` is injected as an init script. It patches `window.fetch` behind `__grokBridgeFetch`, which attaches `x-statsig-id` (generated by intercepting Grok's own statsig middleware module from its Next.js chunks — see `discoverStatsigChunkSource`, which scans `/_next/static/chunks/` scripts and caches the URL+moduleId globally) and streams the response body back to Node via `exposeBinding` callbacks (`__grokBridgeMeta` / `__grokBridgeChunk` / `__grokBridgeDone` / `__grokBridgeError`). Chunks are batched per `BROWSER_STREAM_BATCH_MAX_CHARS` / `_DELAY_MS`.
2. Node side: `BrowserSession.request()` registers a pending request with an in-flight timeout (`BROWSER_REQUEST_TIMEOUT_MS` → HTTP 504). It also keeps a cache of removed DOM nodes and shims `querySelectorAll`/`getElementsByClassName` to survive Grok's anti-bot DOM teardown.
3. `validatePage()` detects Cloudflare blocks and login redirects; `ensurePage`/`recreatePage`/`recreateContext` recover from transient protocol errors; `dismissModals` clicks through ToS/cookie popups.

### Streaming pipeline

`GrokClient.streamRequest()` POSTs to `/conversations/new` or `/conversations/:id/responses` and feeds the NDJSON body to `createNdjsonParser` → `applyGrokEvent(state, payload)`, which accumulates conversation/userResponse/modelResponse ids, thinking vs. visible tokens, and the final `modelResponse` payload into a `state` object. Two stream shapes are handled: `/conversations/new` nests details under `result.response`, follow-ups put them at `result.*`.

If the stream ended without a complete `modelResponse` (e.g. thinking-only streams), `hydrateMissingModelResponse()` polls `load-responses` with backoff (`RESPONSE_HYDRATION_DELAYS_MS` / `RESPONSE_HYDRATION_THINKING_DELAYS_MS`).

**Streaming invariant:** provisional/thinking tokens are never emitted to the OpenAI client. `applyGrokEvent` only accumulates `messageTag === "final"` deltas into `assistantText`/`assistantVisibleText`, so thinking-phase and `response_start` markers never leak. `createProgressiveTextStream` (openai/progressive-text-stream.js) forwards visible deltas to the client live, normalizes Grok markdown whitespace, and at `finish()` emits `getFinalTextSuffix` (grok/output.js) — the corrected tail when the canonical `modelResponse.message` diverges from the live stream. This is also why SSE prelude events (`response.created`, assistant role chunk) are emitted lazily via `onActivity` — **Grok rejects the upstream request if SSE bytes are written before it starts streaming**; keep preludes tied to the first observed visible token.

### Accounts, failover, model fallback

- `GrokAccountPool` builds one `GrokClient` per cookie set (concatenated Netscape blocks in `GROK_COOKIE_FILE` / `GROK_COOKIES_TEXT`), each with an isolated profile dir `account-NNN`. Cookie file hot-reloads on change; malformed updates keep the last known-good pool. Clients are closed when idle so reloads don't leak browsers.
- `withFallback` runs the operation on the primary account, then rotates through fallbacks deterministically. Session-unavailable errors (`grok_session_blocked`, 401/403/429/503, rate-limit/auth message heuristics in `isSessionUnavailableError`) quarantine an account for a 15-minute cooldown; after two wrapped fallback passes the request fails.
- `withFastModelFallback` (model-fallback.js): "Model is not found" or timeouts on premium modes retry once in `grok-4.6-fast`; unsupported premium modes are cached per account (`client.unsupportedModes`).

### Continuation and history

`previous_response_id` follow-ups (`openai/continuation.js`) first try `addResponse` on the account that owns the stored Grok thread (`record.grok.accountIndex` + conversation ids). On failure they replay the stored conversation history: `buildConversationHistory` persists each turn's text + attachments (images re-fetched via `grokAccounts.fetchAsset`) into the file/Postgres store, then `buildReplayConversationRequest` reconstructs a transcript prompt and re-uploads attachments as a fresh conversation.

### Storage and images

`src/store/` has filesystem (`.data/`) and PostgreSQL (`DATABASE_URL`) backends behind the same `fileStore`/`responseStore` interface. Generated images are rehosted to PixelVault (`src/pixelvault/client.js`) so Responses can return `image_generation_call` items with public `result_url`s; Chat Completions returns Markdown plus `message.image_urls`. Streaming emits image items only after final URLs are known.

## Gotchas

- `config.js` is loaded at import time from `.env`; the server and all stores read from this single object. `grokAccounts.init()` runs after `listen()` and pre-initializes the primary account's browser.
- Rate-limit (`429`) and stream-error classifications live in `stream-parser.js` (`applyGrokEvent`) and `client.js` (`inferModelResponseErrorStatus`); they gate account quarantine, so change them carefully.
- Responses `store: false` still stores the response — replay and `GET /v1/responses/:id` depend on it.
- `conversation`, tool calling, and `n > 1` are intentionally not implemented (README "Compatibility notes").
- `src/openai/` never imports from `src/grok/` directly — the server wires them; keep it that way so each side stays testable.
